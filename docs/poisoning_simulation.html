Simulating untrustworthy clients

This branch adds model-poisoning clients to both the simulator (simple/simulate_fl.py) and the deployed system (distributed/). It also adds the server-side rules and learned controllers that have to cope with them. This page lists what each attack does, where it runs, which defenses face it, and what is not simulated.

3 attack typesstandard (×5), stealth (norm-matched), flip (reverse direction)
On/off scheduleattackers can be active only in chosen rounds

Threat model

  • Who: a fixed set of --num-malicious clients, drawn once per seed from all clients (seed stream 0xBAD), so every method sees the same attackers for a given seed. The default experiment uses 20 of 100.
  • What they control: only the weights they upload. Each malicious client trains honestly on its own data, then rewrites its update before uploading it. Its data and labels are not poisoned.
  • When: only in rounds where the client selector picks them, and only in rounds listed in --attack-rounds. By default they attack in every round.
  • What the server has: a clean validation set V (half of the pooled test records per seed). It never sees which clients are malicious, with one exception for Krum (see below). The test set T is reported only and is never used for any decision.
1 · selectOort or random picks K = 20 clients
2 · trainevery selected client runs E = 5 epochs of plain SGD honestly
3 · attackmalicious clients rewrite Δ = wlocal − wt before upload
4 · serverthe controller applies one or more rules, possibly scoring them on V
5 · reportmetrics of wt+1 on T, and n_malicious for the round

Attack vectors

Every attack has the same form. The client uploads wt + s·Δ, where Δ is its honest update and s sets the direction and norm:

AttackFlagUploadWhat it testsRuns in
standard --attack standard wt + 5·Δ (scale from --attack-scale) A "loud" outlier: right direction, too large. This is FedStrategist's attack (Haque et al. 2025, Sec. 4.3). simulator deployed client
stealth --attack stealth Same direction as Δ, rescaled to the mean norm of the round's benign updates An attacker that norm-based filters cannot tell apart from honest clients. simulator only, since it needs every other client's update
flip --flip (combines with either attack, or with none) wt − Δ, wt − 5·Δ or a reversed stealth update Actual poisoning: the update pushes the model away from fitting the data. This is an extension; FedStrategist has no such attack. simulator deployed client
on/off schedule --attack-rounds 1-40,81-120 Malicious clients upload honestly outside the listed rounds A non-stationary environment, as in SARA's setting. A learned controller has to notice the change. simulator only

Trainable weights only. The attack rescales only the trainable weights. BatchNorm moving statistics stay honest, because scaling a variance delta can make the variance negative, and no aggregation rule is designed to defend against that. A test covers this (test_standard_scales_trainable_delta_only).

Running it

Simulator, with 20 of 100 clients attacking at 5× and reversed, active only in two windows:

cd simple
python simulate_fl.py -a fedavg --num-malicious 20 --attack standard --flip \
    --attack-rounds 1-40,81-120 -o results/demo_poison

Each round row in metrics.csv includes n_malicious, the number of attackers among that round's selected clients, and the console marks their lines (malicious).

Deployed system: the client takes --attack / FL_ATTACK (none or standard), --attack-scale / FL_ATTACK_SCALE and --flip / FL_ATTACK_FLIP. The server and the Celery worker take FL_NUM_MALICIOUS, which only sets Krum's f. To make client_3 malicious, add an override file:

# override.yml
services:
  server: { environment: { FL_AGGREGATOR: fedstrategist, FL_NUM_MALICIOUS: "1" } }
  celery: { environment: { FL_AGGREGATOR: fedstrategist, FL_NUM_MALICIOUS: "1" } }
  client_3: { environment: { FL_ATTACK: standard } }

docker compose -f docker-compose.yml -f override.yml up

What the server can do about it

Defenses are plugins in distributed/server/plugins/, and the simulator and the deployed server use the same code. A rule combines one round's updates into a candidate model. A controller decides which rule's candidate to keep each round.

Rules

RuleHow it combines updatesAgainst these attacks
fedavgSample-size-weighted meanNo defense; the undefended baseline.
medianCoordinate-wise median (the lower middle value for an even count)Ignores a minority of large or reversed coordinates.
krumKeeps the one client model with the smallest sum of squared distances to its n − f − 2 nearest neighboursDrops outliers. Falls back to FedAvg when n ≤ 2f + 2.
fedyogiAdaptive server step on the FedAvg pseudo-gradientNot robust; it is in the rule set for Papers 1 and 2.

Controllers and their arms

ControllerArms or candidates (poisoning runs)How it choosesModels scored on V per round
select (Paper 1)3: fedavg, median, krumNo bandit; nothing about the choice carries over between rounds. Builds all three candidates, scores each on V and keeps the one with the lowest loss. This is the selector H12–H15 use.3
select_train (Paper 2, the system default)3: fedavg, median, krumSame choice as select, then the server trains the kept model on V: 1 epoch of SGD at the client learning rate (--ft-epochs, --ft-lr-scale). Without --select-frac, the same V is used for scoring and training. Not in the H12–H15 commands as written.3, plus 1 training pass
fedstrategist3: fedavg, median, krumContextual bandit: paper = LinUCB, authors = CountUCB. The context is 3 update diagnostics (variance of norms, mean cosine similarity, norm of the mean), plus a bias term in the paper preset. Reward = 100·Δaccuracy on V − 0.5·cost(rule), or the drop in loss with --fs-reward loss.1 (2 in round 1)
sara3: fedavg, median, krumUCB1 with no context. Tries each arm once, then picks mean + c·√(2 ln t / na). Reward = accuracy − loss on V. Reconstructed from the TMLR paper's description, since there is no public code.1

Pass --rules to change any controller's arm set; the number of arms is the number of rules given. The client selector is a separate learner: Oort treats each client as an arm (100 here) and picks 20 per round. It is trained independently of the server controller, so the system does not learn a joint client-and-rule choice.

Krum is given the true f in the simulator. The simulator sets Krum's f to the exact number of attackers among the selected clients that round, which no real server knows. This favours Krum. The deployed server uses the fixed FL_NUM_MALICIOUS instead. Pass --rule-args '{"krum": {"num_malicious": 4}}' to fix f in the simulator too.

Other trust mechanisms in the deployed system

These are not poisoning defenses: they stop outsiders, not authorised clients that misbehave. They were already on main.

  • Client authentication: challenge-response. The server issues a random 32-byte challenge that expires after 5 minutes. The client answers with SHA-256(stored password hash + challenge), which the server checks in constant time. The session lasts 24 hours in Redis, and the WebSocket refuses clients without one.
  • TLS certificate pinning: the client checks the server certificate's SHA-256 fingerprint (--fingerprint) to stop man-in-the-middle attacks.

Not covered

GapStatus
Backdoor attacks (a trigger pattern that flips predictions only when present)not implemented
Data poisoning such as label flipping (the attacker changes its training data, not its upload)not implemented
Adaptive attackers that know the defense, and colluding attackers that coordinate their uploadsnot implemented Attackers act independently; stealth only matches the norm.
Lying to the client selector: in the deployed system a client reports its own Oort utility and could inflate it to be picked more oftennot simulated In the simulator, utility comes from honest training.
Trimmed mean, Multi-Krum, FLTrust, Zenonot implemented FLTrust and Zeno are needed for H17.
Stealth and on/off attacks on the deployed systemsimulator only

Removed from main: the MAD norm filter (filter_poisoned_clients), which dropped updates with norm z-score above 3 before FedAvg, was removed along with the old server/aggregator.py. FedAvg on this branch is undefended; robustness comes from choosing median, krum or a controller over them. Re-adding the filter as a rule plugin would make it comparable with the others.

Tests

  • distributed/tests/test_plugins.py:
    • The standard attack scales only the trainable weights.
    • The stealth norm matches the benign mean, flip reverses the update, and stealth without a benign norm raises an error.
    • client/attacks.py is byte-identical to the server copy.
    • Median takes the lower middle value; Krum drops an outlier and falls back to FedAvg.
    • Both FedStrategist presets run and persist state, and its reward is computed correctly.
    • SARA updates only the arm it applied.
  • simple/tests/test_simulate_fl.py: test_poisoning_and_attack_rounds checks that attackers are active only in the listed rounds (n_malicious = 0, then 3). Every controller runs end to end.
